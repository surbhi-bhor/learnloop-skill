# Profile and teaching styles

Read this reference for the `teach` command and when creating the Profile page.
The profile supplies context for examples; the style changes how an explanation
is presented, not what is true.

## Profile page fields

Keep this page private. Leave fields blank until the user supplies the facts.

- Current and past roles, including years and scope
- Experience to connect from, such as backend services, infrastructure,
  analytics, finance, or testing
- Target roles and seniority
- Portfolio projects and links
- Resume or LinkedIn source material, only when the user chooses to provide it
- Default teaching style and any notes about what makes an explanation useful

Treat examples of backgrounds and roles as prompts, not as assumptions about
the learner. Do not create resume, project, or achievement details.

## Style selection

Use a style named in the current request before the profile default. If neither
specifies a style, use **Plain language first**. The user can switch styles at
any time. Do not infer that a style worked from the user's identity or from one
positive reaction; only record a style as successful after an explicit,
style-free teach-back passes the topic's key points.

| Style | How to present the topic | Limit to state |
|---|---|---|
| Plain language first | Use direct words and explain one mechanism at a time; add code with actual output when useful. | It can take more space than a compact expert summary. |
| New to this topic | Define terms before using them and build from prerequisites. | Keep the real mechanism intact; do not remove essential details. |
| Like I'm 5 | Use a familiar, concrete analogy before the technical explanation. | Name the point where the analogy stops matching reality. |
| Bridge from my experience | Map a verified profile experience to the new concept, then identify the difference. | Do not invent experience or imply the systems behave identically. |
| Gossip | Use a short cast or conflict to make relationships memorable, then translate each part back to the real system. | The story is a memory aid, not evidence. |
| Bollywood | Use a compact plot with a setup, complication, and resolution, then map it to the actual mechanism. | Label dramatization and state where the plot breaks down. |
| Production war story | Explain through a realistic incident, symptoms, diagnosis, and mitigation. | Mark hypothetical details; do not present an invented incident as a real case. |
| My own | Ask for the user's requested format if it is not already described. | Keep the same accuracy, recap, analogy-limit, and check-question rules. |

## Required shape for a styled explanation

1. State the concept and its purpose in direct language.
2. Explain the mechanism accurately. If using an analogy or story, map its parts
   back to the actual system.
3. Add a two-sentence **In plain terms** recap without the style framing.
4. State where the analogy or story stops matching the real mechanism. For a
   direct explanation without an analogy, give the key boundary or common
   misunderstanding instead.
5. End with at least one question that checks the concept without relying on
   the analogy or story.

Do not claim that matching a preferred style improves learning. The modes are
presentation choices. Keep any claims about practical use, job expectations,
or production incidents separate and evidence-based; those belong to the later
reality-card phase.
